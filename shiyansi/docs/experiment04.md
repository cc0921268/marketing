# 实验4：AI + Python 消费者洞察引擎（v0.4 · 蓝牙耳机品类）

> **一句话结论**：把实验2 的语义编码口径与实验3 的 282 条清洗数据串成闭环——规则引擎编码 → pandas 统计（全部占比带分母）→ 三段式洞察报告（事实/推断/建议）→ 每个核心痛点绑定 ≥3 条可回查证据。人工抽检 10 条编码，**情绪一致率 100%、痛点一致率 100%**（课程目标 ≥80%）。

---

## 1. 本实验解决的营销问题

小米要在蓝牙耳机市场守住份额，光知道"均价多少、评分几何"（实验1）不够，还得回答：

> **用户到底在抱怨什么？哪个抱怨最普遍？哪个品牌在哪方面挨骂最多？——以及，这些结论的证据在哪里？**

这三个问题层层递进：抱怨分类是**编码问题**（实验2 的 Skill 口径），普遍程度是**统计问题**（pandas），证据是**追溯问题**（review_id → 原文）。本实验把三者拧成一条可复算的流水线。

**边界声明**：数据为合成模拟，结论仅演示方法，不代表真实品牌口碑。

## 3. 输入数据、来源与字段

### 3.1 数据流

```
data/processed/clean_data.csv（实验3 产物，282 条，只读）
        │
        ├─ encode_batch() 语义编码（全部 282 条，含拒答）
        │     └─ encoding_results.json（282 条编码结论，逐条可审计）
        │
        └─ filter_valid() 过滤（is_valid_review=1 且 is_consistent=1）
              └─ 260 条有效样本 → 统计层
```

### 3.2 关键分母口径（本实验最重要的设计决策）

| 统计 | 分母 | 为什么 |
| --- | --- | --- |
| 情绪分布 | **282**（全部编码记录） | 拒答必须被看见，否则"数据质量多差"这件事被隐藏 |
| 痛点排行 | **260**（有效评论） | 噪音没有分析价值，不应稀释痛点占比 |
| 品牌交叉 | **各品牌评论数** | 每格 `n/该品牌总数（%）`，跨品牌可比 |

两个分母并存是**刻意的**：情绪分布回答"数据整体什么样"，痛点排行回答"有效用户在抱怨什么"。混用一个分母会同时污染两个问题的答案。

### 3.3 痛点分类体系（9 类，从数据实际归纳）

| 维度 | 关键词示例 | 数据中模板数 |
| --- | --- | --- |
| 音质 | 低音、中高频、发刺、糊、刮耳、轰头 | 28 |
| 续航 | 续航、没电、电池、一天两充、掉电 | 28 |
| 佩戴舒适 | 耳朵、耳塞、腔体、耳压、头晕、塞不进去 | 28 |
| 售后服务 | 客服、保修、换货、寄回、价格保护 | 27 |
| 降噪 | 降噪、隔音、吵、听不见报站 | 27 |
| 做工质感 | 做工、划痕、手感、颜值、开合 | 25 |

## 4. 新增功能、Skill 或 Workflow

### 4.1 语义编码：小句级极性判定（本实验核心技术点）

**为什么必须切小句**——这是开发中抓到的最大 bug：

```
原逻辑（整句判极性）：
  "降噪给力，可惜AirPods 3续航一般"
  → 整句含"可惜"（负向线索）→ 降噪、续航都被判为痛点 ❌（降噪是好评！）

新逻辑（切小句 + 转折词切分）：
  ["降噪给力"] ["可惜"] ["续航一般"]
  → 降噪小句 positive → 不是痛点 ✓
  → 续航小句 neutral + 前句有转折 → 痛点 ✓
```

三条判定规则（按优先级）：

| 规则 | 例子 | 判定 |
| --- | --- | --- |
| (a) 本小句负面 | "中高频发刺" → 音质 | 痛点 |
| (b) 本小句中性 + 后小句负面且不属其他维度 | "腔体太大" + "总是掉" | 佩戴痛点 |
| (c) 本小句中性/正向 + 前小句带转折词 | "续航一般" 前有"可惜" | 续航痛点 |

**转折词单独建表**（`但/就是/却/不过/然而/可惜/只是`），不混入负向线索——历史上把它们当负向线索，导致全表负面率虚高 7 个百分点。

### 4.2 编码输出的兼容设计

- `pain_point`（主痛点，schema 必填）+ `pain_points`（全部痛点列表，扩展字段）——一句"降噪差还耳压大"两条都记
- 拒答优先级：**实验3 的 C8 标记 > 引擎自身正则**，保证与上游口径一致
- `confidence` 分级：判断字段数 + 证据覆盖面 → high/medium/low

### 4.3 统计层（全部 pandas，AI 不参与算数）

| 函数 | 产出 | 校验 |
| --- | --- | --- |
| `sentiment_distribution()` | 情绪分布（5+1 类） | 内置 assert：五类+拒答 == 分母 |
| `pain_ranking()` | 痛点排行 | 分母=260；同评论同维度去重；排序降序 |
| `brand_sentiment_stats()` | 品牌×情绪 | 每格 `n/品牌数（%）` |
| `brand_pain_cross()` | 品牌×痛点 | 行合计列"痛点总数" |
| `top_evidence()` | 证据抽取 | 互动量降序 → 评分升序，取 k=3 |

### 4.4 AI 解释模块：三段分离

`build_insight_report()` 只接收统计表，**不接触原始零散文本**：

- **一、事实数据**：只陈述表格里有的数字，每个占比带分母
- **二、推断假设**：每条推断必须附"依据"+"边界"（如"差距在个位数时应视为同一梯队"）
- **三、行动建议**：9 类痛点各配具体动作（如降噪→"详情页用实测 dB 曲线替代形容词"），不接受"加强优化"式空话
- **四、证据追溯**：TOP5 痛点各 3 条证据（review_id + 原文 + 逐字片段）
- **五、方法说明**：编码方式、分母口径、局限（规则引擎弱于大模型的场景：否定句、反讽）

**红线**：报告不出现"质量差/最差/千万别买"等绝对化断言（测试强制）；必须含"模拟数据"声明。

## 5. 程序计算与 AI 判断的分工

| 环节 | 负责方 | 实现位置 |
| --- | --- | --- |
| 读取、过滤、分母确定 | 程序（pandas） | `load_clean / filter_valid` |
| 语义编码（本版为规则引擎） | 程序（Skill 口径的确定性实现） | `encode_review / encode_batch` |
| 痛点计数、占比、排序 | 程序（pandas） | `pain_ranking / sentiment_distribution` |
| 品牌交叉统计 | 程序（pandas） | `brand_sentiment_stats / brand_pain_cross` |
| 证据抽取与排序 | 程序（pandas） | `top_evidence` |
| 洞察解释（事实/推断/建议） | **AI 层**（本版为模板化实现，接口已就绪） | `build_insight_report` |
| 大模型 API | **尚未调用**（实验7 接入，替换解释层即可） | — |

> **为什么本版用规则引擎而非大模型**：可复现（同输入必同输出）、可测试（160 项断言）、离线可跑、无需 API key。`encode_review()` 与 `build_insight_report()` 已是可插拔接口，实验7 换 LLM 实现时统计层零改动。

### 6.3 Debug 记录（按发现顺序）

**坑 1：转折词被当负向线索，全表负面率虚高**
`NEGATIVE_CUES` 最初含"但/就是/却/不过"，导致"音质没得说，就是连接抽风"整句判负面。修复：转折词独立建表，只做极性切换信号。负面率从 63.1% 修正为 56.4%。

**坑 2：整句极性误伤好评维度**
"降噪给力，可惜续航一般" → 降噪被误标痛点。修复：**小句级极性判定**（§4.1），并在转折词处二次切句（"音质和降噪都不错，但…耳朵疼"中"但"在小句内部）。

**坑 3：关键词过严漏判**
"耳朵疼"匹配不到"耳朵**就**疼"。修复：关键词改用短词根（"耳朵"而非"耳朵疼"），音质补"轰头/齿音/破音"。

**坑 4：拒答恒为 0**
先 `filter_valid` 后编码，噪音根本没进编码器。修复：`encode_batch` 对**全部** 282 条编码并透传 `upstream_invalid`，拒答正确显示 15 条，与实验3 的 C8 对齐。

**坑 5：情绪分布重复计数**
拒答记录的 sentiment 恒为 unknown，导致"无法判断 23 = 真无法判断 8 + 拒答 15"。修复：统计"无法判断"时排除拒答行，并加 assert（五类+拒答 == 282）。

**坑 6：证据 quote 跨小句失真**
证据截取以整句为底，可能跨过逗号包含别的维度。修复：证据锚定在命中小句内，保证"逐字子串 + 语义聚焦"。

### 6.4 与统计口径相关的两个说明

1. **痛点计数是多选题口径**：一条评论抱怨两个维度则各计 1 次，因此 9 类之和（173）> 分母（260 中的 160 条有痛点）。报告与页面均有说明。
2. **"做工质感"零提及**：9 个维度全部扫描，但本期数据中该维度无负面抱怨（数据里"做工漂亮/颜值高"均为好评）。报告以"零提及维度 = 相对优势项"单列说明，而非从表中删除——**"没检查"和"检查了没人抱怨"是两回事**。

## 8. 已知限制与合规说明

**限制**：

1. 规则引擎的语义理解弱于大模型：否定句（"不是不行"）、反讽（"真是绝了"）、隐含抱怨（"再也不会回购了"）可能漏判或误判
2. 抽检 10 条全部正确，但样本小；大规模换数据后一致率需重新抽检（测试 `test_encoding_spotcheck_rate` 可直接复跑）
3. 痛点关键词表从本数据集归纳，换数据集需校准（同实验3 的 C6 价格上限）
4. 转折词规则是启发式：多重转折（"虽然…但是…不过…"）嵌套两层以上可能判错
5. 场景识别只取第一个命中（"地铁和办公室都用"只记地铁）
6. 合成数据，结论不可外推为真实市场判断

**合规**：

- 数据只读自实验3 产物，无新采集行为，不涉及 PII
- 报告含"模拟数据"声明，无绝对化商业断言（测试强制）
- 证据引用均为原文逐字子串，可审计
- 9 类痛点与关键词表公开在本文档 §3.3，公式透明
