# 实验3：营销数据获取与清洗（v0.3 · 蓝牙耳机品类）

> **一句话结论**：为蓝牙耳机品类搭建了一条**合规、可复现、可追溯**的数据处理管线——用固定种子合成 300 条含 10 类真实噪声的原始数据，经 10 条清洗规则处理得到 282 条干净数据，整体字段完整率 **97.82%**（达标线 90%），全部处理过程落在 731 行日志里，逐条可回溯到原始值。

---

## 1. 营销问题

### 1.1 我们要回答什么

后续实验（消费者洞察、竞品分析、内容生成、投放优化）都建立在一份数据上。如果这份数据本身不可信，后面所有结论都是沙上建塔。所以实验3 要解决的**不是营销问题，而是"营销问题能不能被回答"的问题**：

> 在蓝牙耳机这个红海品类里，我们能否拿到一份**噪声可控、口径统一、可审计**的评论数据，让后续"哪个品牌的降噪口碑最好"、"用户抱怨集中在哪"这类问题有可靠答案？

### 1.2 为什么必须做清洗

真实的电商评论数据长这样（本项目刻意模拟）：

| 现象 | 后果 |
| --- | --- |
| 同一个索尼写成 `索尼`/`SONY`/`Sony`/`新力` | 品牌分组统计变成 4 个"不同品牌"，每家的样本量都被稀释 |
| 价格写成 `￥599.00`、`599元`、`1,299`、`€599` | 无法算均价，无法做价格带分布 |
| 同一条评论被提交两次 | 该用户的态度被双倍加权，均值被拉偏 |
| 评分出现 8.7（其实是 10 分制） | 均值算出 4.9 这种不可能的数字，且极值污染方差 |
| 评论是 `。。。。。` 或 `加我微信xxx` | 情感分析在噪声上做无用功，还可能算出"中性"污染词频 |
| 华为品牌配 Redmi 型号 | 品牌-型号交叉分析全错 |

**这些不是假设，是本项目数据里真实存在的**（见 §4 与 `cleaning_log.csv`）。

### 1.3 边界声明

本实验**只交付数据**，不做洞察、不做结论。数据为**模拟合成**，品牌与型号名参考公开市售信息仅为让数据合理，**评论内容不代表任何真实产品口碑**。

## 3. 输入数据

### 3.1 双通道设计

```
通道A（主）                          通道B（辅）
programmatic synthesis               public dataset adapter
src/generate_raw_data.py             src/fetch_public_data.py
        │                                     │
        ▼                                     ▼
data/raw/raw_data.csv                data/raw/public_slice.csv
300 条 · 10 类噪声                    + public_slice.meta.json
        │                            60 条 · 仅验证字段映射
        └──────────────┬──────────────────────┘
                       ▼
              src/data_cleaning.py
              C1—C10 十条规则
                       ▼
        data/processed/clean_data.csv   282 条
        data/processed/cleaning_log.csv  731 行
        data/processed/quality_report.json
```

**为什么双通道**：合成数据保证"噪声可控、可复现、统计口径可解释"；公开数据适配器证明"这套字段映射在真实数据上也能跑通"，而不是只会在自己造的数据上自嗨。两者不混合统计——混进来只会让完整率失去意义（公开切片本身 price/date 全空）。

### 3.2 数据规模与分布

| 项 | 值 |
| --- | --- |
| 原始条数 | 300 |
| 品牌 | 6（Apple / 华为 / 小米 / 漫步者 / OPPO / 索尼） |
| 产品型号 | 23 |
| 日期范围 | 2024-01-01 ~ 2024-06-28 |
| 价格带 | 约 100 ~ 2200 元 |
| 评分 | 1.0 ~ 5.0（异常时出现 7.5—10.0 的 10 分制） |

### 3.3 注入的 10 类噪声

| 编号 | 噪声 | 比例 | 例子 |
| --- | --- | --- | --- |
| N1 | 品牌别名 | ~80% 行 | `EDIFIER` → 漫步者，`華為` → 华为，`新力` → 索尼 |
| N2 | 价格脏格式 | ~65% 行 | `￥398.56`、`599元`、`1,299.00`、`€599` |
| N3 | 价格 ×10 | 2% | 真实 599 → 记成 5990 |
| N4 | 日期 5 种格式 | ~60% 行 | `2024-06-01` / `2024/6/1` / `20240601` / `2024年6月1日` / `6/1` |
| N5 | 字段缺失 | price 4% / rating 8% / interaction 6% / text 2% | 空串 |
| N6 | 整行完全重复 | 3%（9 行） | 8 个字段逐字节相同 |
| N7 | ID 重复 | 3%（9 行） | 同 ID 但 rating / interaction 不同 |
| N8 | 无效评论 | ~5%（15 条） | `。。。。。`、`666666`、`加我微信xxx`、`天气不错` |
| N9 | 繁简 / emoji 混用 | ~12% | `續航`、`藍牙連接不穩`、😂👍、全角 `５９９` |
| N10 | 逻辑矛盾 | rating 2% / 未来日期 1% / 张冠李戴 4.5% | 8.7 分、2024-12-31、华为品牌配 Redmi 型号 |

> **N6 与 N7 的两阶段注入**：这两类必须互斥，否则 C2 和 C3 会退化成同一个计数器。做法是——先造 `300 - 9 - 9 = 282` 条干净底料，再追加 9 条 N7（复制底料行、沿用原 ID、强制改 rating），然后追加 9 条 N6（整行复制），最后 shuffle 并截断到 300。这样"整行重复"和"ID 重复但内容不同"是两类可分别验证的样本。

## 4. 新增功能（C1—C10 清洗管线）

### 4.1 规则总表

| 编号 | 规则 | 处理方式 | 本期命中 |
| --- | --- | --- | --- |
| **C1** | 品牌别名归一 | 查表映射到 6 个规范名；未登记别名保留原值 + 记日志 | **243 条** |
| **C2** | 整行重复 | 完全重复剔 1 条（`keep="first"`） | **9 行** |
| **C3** | ID 重复 | 内容不同保留首条 | **9 行** |
| **C4** | 日期归一 | 5 种格式 → ISO；缺年份补 2024；未来日期置空 | **184 条**（置空 2） |
| **C5** | 价格解析 | 三段式：欧式小数 → 千分位 → 剥离符号 | **201 条**（失败 0） |
| **C6** | 价格异常 | 超上限 winsorize 截断（不删行） | **2 条** |
| **C7** | 缺失分级 | text/brand 缺→删行；price/rating 缺→留空；interaction 缺→填 0 | 填 0 **14**，price 置空 **13**，rating 置空 **28**，删行 **0** |
| **C8** | 无效评论 | 打 `is_valid_review=0`，**不删** | **15 条** |
| **C9** | 文字形态 | 繁简归一 + 剥 emoji + 全角字母数字→半角；**中文标点保留** | **36 条** |
| **C10** | 逻辑矛盾 | rating 超范围 ÷2 折算；品牌型号不匹配打 `is_consistent=0` | 折算 **8**，标记 **7** |

### 4.2 三个值得说的设计决策

**决策一：C6 用截断，不用删行。**
价格 `5990` 明显是 599 的 10 倍录入错误。直觉做法是删掉，但删掉会引入系统偏差——如果错价集中在高价型号（更贵的耳机更容易被手工录错），删行就等于系统性剔除高端样本，价格分布会左偏。所以用 **winsorize**：把超上限值压到 `min(品牌上限, IQR上须×3)`，行保留。

**决策二：C8 只打标，不删。**
无效评论（`。。。。。`、`加我微信xxx`）删掉最省事，但删掉后就**无法证明**我们识别过它们。保留 + 打标，下游（实验4 洞察、实验2 Skill）可以自己决定"要不要用"，审计链完整。这和"数据清洗应该可逆、可审计"的原则一致。

**决策三：C7 分三级处理，不是一刀切。**
- `review_text` / `brand` 缺失 → **删行**（这两个是核心分析对象，缺了这条数据没意义）
- `price` / `rating` 缺失 → **留空**（保留行，后续统计算均值时 `skipna`，不污染方差）
- `interaction_count` 缺失 → **填 0**（有明确业务依据：没有互动就是 0，不是"未知"）

这三级的区别是本实验和"粗放清洗"最大的分野：**填 0 是有业务依据的补全，填均值是伪造数据。**

### 4.3 派生字段

| 字段 | 取值 | 用途 |
| --- | --- | --- |
| `is_valid_review` | 0/1 | C8 标注；实验4 可据此过滤或单独统计噪音占比 |
| `is_consistent` | 0/1 | C10 标注；实验4 做品牌-型号交叉分析前应先筛 `is_consistent=1` |

## 5. 程序与 AI 的分工

| 环节 | 谁做 | 具体分工 |
| --- | --- | --- |
| 噪声体系设计 | **人** | 10 类噪声的选择与比例是业务判断："真实电商数据会脏在哪"，AI 无法凭空知道 |
| 生成器编码 | AI 写，人审 | AI 实现两阶段注入、别名池、繁简映射；人负责验收"噪声是否真的注进去了" |
| 清洗规则设计 | **人** | C1—C10 的每一条都对应一个业务后果（见 §1.2），规则边界（如"短评算不算噪音"）由人拍板 |
| 清洗代码实现 | AI 写，人审 | AI 实现 pandas 逻辑；人审"是否误伤" |
| Bug 定位 | **AI 为主** | 3 个关键 bug 由测试失败反推定位（见 §6） |
| 修复方案 | 人定方向，AI 实现 | 如"C9 该不该转中文全角标点"是人的判断，AI 负责改代码 |
| 文档 | AI 起草，人补充业务语境 | 数字全部从 `quality_report.json` 取，不手写 |

**核心原则**：AI 擅长"把规则写成代码"，人负责"规则该是什么"。本项目里 AI 写出过 3 个有隐蔽 bug 的版本，都是靠人设计的测试断言抓出来的。

## 6. 测试结果与 Debug

### 6.1 测试规模

```
$ python3 tests/test_cleaning.py
合计 88 项，通过 88 项，失败 0 项。
```

88 项测试覆盖：生成器（可复现/300 条/N1—N10 逐类验证）+ C1—C10 逐规则边界 + 端到端（raw 不被改、幂等、完整率、品牌收敛数、日志结构）。

### 6.2 抓出来的 6 个坑（按发现顺序）

**坑 1：C5 把空价格也记为"解析失败"（20 条误报）**

`str(None)` 得到 `"None"` 而不是空串，所以 `if not s:` 这个守卫失效，20 条缺失价格被当成"格式脏解析不了"记进 C5 日志。**这是典型的"缺失"与"脏值"混淆**。

修复：加 `raw_is_blank` 前置判定（`None` / `NaN` / 全空白），缺失归 C7 管，C5 只处理"有值但格式脏"的。测试 `test_c5_blank_price_no_log` 卡住这条。

**坑 2：C9 把中文全角逗号转成半角，破坏 249 条评论**（最严重）

最初用 `range(0xFF01, 0xFF5F)` 做全角→半角映射。这个区间**包含全角标点** `，。！？：；`，于是 "续航一般，蓝牙连接不稳。" 变成了 "续航一般,蓝牙连接不稳."。249 条本来完全正常的评论被"修坏"了。

修复：收窄为三组显式映射，只转 `０-９` / `Ａ-Ｚ` / `ａ-ｚ`：

```python
_FULLWIDTH_ALNUM = {
    **{chr(0xFF10 + i): chr(0x30 + i) for i in range(10)},
    **{chr(0xFF21 + i): chr(0x41 + i) for i in range(26)},
    **{chr(0xFF41 + i): chr(0x61 + i) for i in range(26)},
}
```

C9 命中数从 249 降到 36（真实需要修的只有繁简、emoji、全角数字）。**教训：全角/半角转换必须按字符类别白名单，绝不能按码位区间。**

**坑 3：繁体字一个都没注入（C9 繁简规则恒命中 0）**

`_traditionalize()` 里 `for simp, trad in TRAD_TO_SIMPLE.items()` 遍历方向写反了——表的 key 是繁体、value 是简体，写成 `for k, v` 后用 `replace(k, v)` 等于把繁体替换成简体，而输入本来就是简体，所以什么都没发生。

修复：改为 `for trad, simp in TRAD_TO_SIMPLE.items(): out = out.replace(simp, trad, 1)`。

**坑 4：C3 ID 去重恒为 0 条，C2/C3 退化成一类**

两个叠加原因：(a) N6 和 N7 在同一次循环里交替掷骰，N7 造出来的行被 N6 的整行复制覆盖；(b) 命中率 `int(300*0.015)=4` 太低。

修复：改**两阶段注入**（§3.3），N7 沿用原 ID 复制底料行并强制改 rating；比例提到 3%。

**坑 5：张冠李戴只命中 1 条**

`foreign = [p for p in ALL_PRODUCTS if p != product]` —— 这样可能取到**同品牌其他型号**，那就不算张冠李戴了。

修复：改按规范品牌取差集 `own = {p[0] for p in PRODUCTS[brand]}; foreign = [p for p in ALL_PRODUCTS if p not in own]`，比例提到 4.5%。

**坑 6：原始数据变成 318 条**

两阶段注入没扣减底料名额。修复：`n_base = n - n_dup_id - n_dup_full`，末尾 `records[:n]` 兜底。

### 6.3 测试本身的两个期望值错误

补测试时还发现自己写错了断言，这类"测试 bug"和"代码 bug"要分开记：

- `test_c10_rating_converted_to_half` 期望 4.4，实得 4.3。原因是 `round(8.7 / 2, 1)` 在 float 下：`8.7/2 = 4.3499999...`，`round(4.35, 1)` 得 4.3。业务上 8.7/2 就该是 4.4，所以**改代码不改测试**，用 `Decimal(...).quantize(0.1, ROUND_HALF_UP)` 做十进制四舍五入。
- `test_c6_price_clipped_not_dropped` 抛 `TypeError: '>' not supported between str and float`。测试构造数据时 price 传的是字符串 `"300"`，而 `c6_clip_price` 处理的是 C5 之后的 float 列。修复：测试里传 `float(...)`（同时也提醒了**函数契约要在 docstring 里写清输入类型**）。

### 6.4 修复后新增的回归测试

- `test_c9_trad_map_covers`：遍历繁简映射表，对 8 条真实样本逐条验证"替换后无残留繁体"。这条专门卡"映射表漏词条"——历史上漏了 `穩→稳`，端到端测试完全看不出来。
- `test_c10_idempotent`：把 C10 输出再喂给 C10，断言二次折算为 0 条，防止重复折算。

## 8. 已知限制

| 限制 | 说明 | 影响 |
| --- | --- | --- |
| 数据是合成的 | 评论由模板拼接，语言多样性远低于真实评论 | 实验4 做文本聚类/主题模型时，真实数据上效果可能显著下降 |
| 品牌/型号名真实，评论虚构 | 便于理解，但容易被误读为真实口碑 | 已在 4 处文档声明；对外汇报必须先说明 |
| 公开切片仅 60 条且不参与统计 | 只验证了字段映射跑得通 | 不能声称"在真实数据上验证了清洗效果" |
| 无时间序列深度 | 6 个月、300 条，做不了季节性或趋势分析 | 实验5 竞争分析只能做横截面 |
| 无用户维度 | 没有用户 ID、复购、会员等级 | 做不了用户分群、LTV 分析 |
| C6 上限靠人工设定 | 品牌价格上限是按公开市价估的 | 真实数据需重新校准，否则截断可能误伤 |
| 简体转换表非完备 | `TRAD_TO_SIMPLE` 只收录了 45 组高频词条，非完整繁简表 | 遇到表外繁体字会漏转；已加 `test_c9_trad_map_covers` 做样本级防护 |
| 未做分词/情感分析 | 本实验只做清洗，不做文本挖掘 | 属实验4 范围 |

## 附：与后续实验的接口约定

| 约定 | 说明 |
| --- | --- |
| 数据入口 | 后续实验**只读** `data/processed/clean_data.csv`，不再碰 raw |
| 过滤建议 | 做品牌-型号分析前先 `is_consistent == 1`；做情感分析前先 `is_valid_review == 1` |
| 缺失口径 | `price` / `rating` 的空值是"未知"，统计时用 `skipna`，**不得填 0 或均值** |
| 派生列 | `is_valid_review` / `is_consistent` 是本实验新增，后续实验可直接使用 |
| 可追溯 | 任何异常数据点都可通过 `review_id` 反查 `cleaning_log.csv` |
